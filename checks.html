Checks explained

What the IIIF Service Dashboard requests and how results are classified

Dashboard View on GitHub ↗

Server behaviour, not full JSON validation

The checker makes HTTP requests to one sample Manifest and one sample Image Service for each project. It concentrates on retrieval, redirects, content negotiation, compression, CORS, media types, identifiers, and a small set of properties needed to recognize the response. Beyond a couple checks on certain values in the JSON responses, it does not validate the IIIF JSON responses.

Each request contributes one result. When several things are wrong with the same response, the report shows the highest-priority diagnostic rather than adding several blocks for one request.

Result colours

Advisories are shown only in the details and do not lower the main API label. Preflight results are also details-only. The health meter counts passes, warnings, and failures.

✓Pass

The request and its primary diagnostic succeeded.

◆Advisory

The response is usable, but an optional or recommended improvement is unavailable.

!Warning

The response is usable, but there is a concrete interoperability or caching risk.

×Fail

The request or required representation is unusable.

Not checked means a limited run deliberately omitted the project. Not tested means there is no configured sample, no observation, or a prerequisite failed—for example, an image cannot be derived from an unreadable info.json.

Presentation API checks

These checks use the configured sample Manifest URL.

Default Manifest response

presentation.default

Sends a GET without an explicit Accept. The context identifies v2 or v3. A v2 Manifest must have @type: "sc:Manifest" and a sequences array; v3 must have type: "Manifest" and an items array. Type values are case-sensitive. The required identifier must match the final URL after redirects.

  • PassRecognizable JSON, matching @id/id, JSON media type, and usable CORS.
  • WarningA non-empty identifier differs from the final response URL, CORS is invalid, or Content-Type is not a JSON media type.
  • FailRequest or HTTP failure, unreadable or invalid JSON, unrecognized context or shape, or a missing, empty, or non-string identifier.

ReferencesPresentation API 2.1 §5.1 · Presentation API 3.0 §5.2

Gzip compression

presentation.compression

Requests the Manifest with Accept-Encoding: gzip and verifies that a declared gzip body can be decompressed as JSON.

  • PassValid gzip-compressed JSON with Vary: Accept-Encoding.
  • AdvisoryA usable identity response is returned; gzip is recommended.
  • WarningGzip works, but Vary: Accept-Encoding is missing.
  • FailRequest/HTTP failure, unsupported encoding, corrupt gzip, or decompressed content that is not JSON.

ReferencesMDN Content-Encoding · MDN Vary

v2 and v3 content negotiation

presentation.v2 · presentation.v3

Makes two GETs with the IIIF v2 and v3 profile-valued Accept headers, then evaluates the pair together.

  • PassThe requested version is returned, or the unavailable version is correctly declined with HTTP 406. When both probes return the same version, the matching response does not need Vary.
  • AdvisoryA different recognizable version is returned. Supporting the requested version is recommended.
  • WarningThe probes return different versions, or success versus 406, but an otherwise-valid successful response lacks Vary: Accept. Default-response warnings can also apply.
  • FailThe negotiated request or returned representation fails the same required checks as the default response.

ReferencesPresentation API 2.1 §7.2 · Presentation API 3.0 §6.3 · MDN Vary

Manifest negotiation preflight

presentation.preflight

Sends OPTIONS with the configured dashboard origin, Access-Control-Request-Method: GET, and Access-Control-Request-Headers: Accept. IIIF profile-valued Accept headers contain quotes and a URI colon, so they are not CORS-safelisted.

  • PassOPTIONS succeeds and permits the origin, GET, and the Accept request header.
  • WarningOPTIONS succeeds but does not list GET or Accept.
  • FailRequest/non-2xx failure or an invalid Access-Control-Allow-Origin response.

ReferencesFetch Standard request-header safelist · MDN preflight requests

Image API checks

These checks use the configured sample info.json and derive an image request and service base URI from it.

Default image information response

image.default

Sends a GET without an explicit Accept. The response must contain numeric width and height. Its v2 @id or v3 id must match the final info.json URL after removing /info.json, query, fragment, and trailing slash.

  • PassRecognizable image information with matching identifier, JSON media type, usable CORS, and a recognized Level 0, 1, or 2 profile.
  • WarningIdentifier mismatch, invalid CORS, non-JSON media type, or no recognized compliance level.
  • FailRequest/HTTP/JSON failure, missing numeric dimensions, or a missing, empty, or non-string identifier.

ReferencesImage API 2.1 §5.2 · Image API 3.0 §5.2

Gzip compression

image.compression

Requests info.json with Accept-Encoding: gzip. Outcomes are the same as the Presentation gzip check: compressed valid JSON passes, usable identity is advisory, missing Vary: Accept-Encoding warns, and unusable compression fails.

ReferencesMDN Content-Encoding · MDN Vary

v2 and v3 content negotiation

image.v2 · image.v3

Requests both Image API profile media types and compares the detected versions. It uses the same paired pass, advisory, 406, and Vary: Accept policy as Presentation negotiation.

ReferencesImage API 2.1 §5.1 · Image API 3.0 §5.1 · MDN Vary

info.json negotiation preflight

image.info-preflight

Sends the same profile-negotiation OPTIONS request as the Manifest preflight. It passes when the origin, GET method, and Accept header are permitted; missing GET/Accept warns; request, HTTP, or ACAO failures fail.

ReferencesImage API 3.0 §7.1 · MDN preflight requests

Base URI to info.json

image.base-redirect

Dereferences the service base URI without following redirects. IIIF recommends HTTP 303 to the checked or declared info.json URI.

  • PassHTTP 303 has a usable Location matching the checked or declared image information URI.
  • Warning303 points elsewhere, 200 returns directly, another redirect code is used, or any other HTTP response is received.
  • FailThe request fails, or a 303 has no usable Location.

ReferencesImage API 3.0 §2 URI syntax

Representative image response

image.response

Uses the smallest declared size, or width 256 when no sizes are declared, to request full/{size}/0/default.jpg. No OPTIONS preflight is required for this ordinary image GET.

  • PassHTTP success with an image/* media type and usable CORS.
  • WarningThe response is delivered but has a non-image media type or invalid CORS.
  • FailRequest failure or non-2xx HTTP response.
  • Not testedNo image request is possible because the default info.json could not be parsed.

ReferencesImage API 3.0 §4 · Image API 3.0 §7.1

CORS behaviour

The checker sends Origin: https://rism-digital.github.io by default. A response has usable CORS when it contains exactly one Access-Control-Allow-Origin value and that value is either the configured origin or *. Servers may return ACAO only when the request includes Origin; the dashboard records what was returned to its own request.

Accept is normally a CORS-safelisted request header, but only when its value does not contain a CORS-unsafe request-header byte. IIIF content-negotiation values commonly include a quoted profile URI—for example, application/ld+json;profile="http://iiif.io/api/presentation/3/context.json". The quotation marks and the colon in http: are CORS-unsafe bytes, so a client that sends this value must first make an OPTIONS preflight. To permit that request, the preflight response needs a usable Access-Control-Allow-Origin, must allow GET in Access-Control-Allow-Methods, and must include Accept in Access-Control-Allow-Headers. The subsequent GET response still needs its own usable Access-Control-Allow-Origin.

When a server dynamically echoes the allowed origin, Vary: Origin prevents a shared cache from serving one origin’s response to another. The checker records this header but does not score it as a separate rule. Every returned Access-Control-* header is shown in the expanded CORS details.

ReferencesFetch Standard request-header safelist · MDN preflighted CORS requests

Recorded response metadata

The report stores HTTP status, detected IIIF version and level, content type, request Accept value, Location, and returned CORS headers. For each default Manifest and info.json GET it also stores the complete response headers. Every followed redirect retains its URL, status, Location, and complete headers in order.

Results are point-in-time observations from anonymous requests. A later browser request may differ because of conditional headers, caches, firewall policy, rate limiting, or a changed service configuration.
